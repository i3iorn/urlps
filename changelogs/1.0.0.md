# 1.0.0

The theme of this release is a single correction: **urlps was rejecting where
it should have been normalizing.**

Canonicalization was enforced as a validation gate (`require_canonical`) rather
than applied as a transformation. That one design choice caused both of the
problems blocking 1.0 — and they pulled in opposite directions, which is why
neither could be fixed alone.

- **Usability.** Under the default `strict` policy, `parse_url()` rejected
  `http://EXAMPLE.COM/`, `https://example.com:443/`,
  `https://example.com/%7Euser`, `http://example.com/a/./b`,
  `https://user:pass@host/` and `?q=WAITFOR`. No other Python URL parser
  rejects any of these. The first-run experience read as "this library is
  broken".
- **Security.** Turning the gate off — the shipped, documented
  `policy="balanced"` — returned the host **un-normalized**:

  ```python
  parse_url('http://EVIL.COM/',  policy='balanced').host  # -> 'EVIL.COM'
  parse_url('http://evil.com./', policy='balanced').host  # -> 'evil.com.'
  ```

  Both slip past a caller's `host in BLOCKLIST` check.

Normalizing resolves both at once and closes the bypass. That is the spine of
this release; everything else follows from taking the same idea seriously
elsewhere.

## Security fixes

**Host normalization bypass.** `url.host` is now always lowercase, with any
trailing root dot stripped and IPv6 literals canonicalized — under *every*
policy, including `internal`. Allowlist and blocklist comparisons are now
reliable.

**`URL()` was a quieter `parse_url()`.** `URL.__init__` defaulted to the
near-no-op `internal` policy while `parse_url()` defaulted to `strict`, so
`URL('http://169.254.169.254/')` succeeded silently where `parse_url()` raised.
`URL` is the type in every annotation and throughout the README, which made it
the most discoverable way to skip every check. Both now default to `strict`.

**`SecurityPolicy.internal()` disabled SSRF.** A preset users reasonably read
as "internal network, still catch SSRF" caught nothing. It now enforces SSRF;
opting out requires saying so: `internal(enforce_ssrf=False)`.

**Punycode homographs were never analysed.** `has_mixed_scripts()` returned
False for any ASCII string, and its call site was additionally gated on `not
url.isascii()`. Punycode is ASCII. So `xn--pypal-4ve.com` — the A-label form of
`pаypal` with a Cyrillic а, which is precisely how a homograph attack travels —
received no script analysis at all and was **accepted** under `balanced`. The
host is now decoded before analysis.

**IDNA parser differential.** `_parser` hardcoded stdlib `encode("idna")` (IDNA
2003) while `_validation` preferred the `idna` package (IDNA 2008/UTS-46). The
parser won, so the host stored on a `URL` disagreed with the one validation had
checked — even with `idna` installed:

```
https://straße.de/   0.8 -> "strasse.de"        (a different domain)
                     1.0 -> "xn--strae-oqa.de"  (what browsers resolve)
```

**`URL` was mutable.** The README advertised immutable URL objects, but
`u._host = "evil.com"` worked and changed `str(u)` — so a URL that passed
validation could be re-pointed afterwards while still presenting itself as
validated. `URL` now rejects attribute assignment and deletion.

## Security detection

Homograph detection was rebuilt. The old implementation derived a character's
"script" by taking the first word of `unicodedata.name()` and matching an
eleven-entry hardcoded list — a name-prefix hack that missed every script
outside the list and misclassified anything named `FULLWIDTH ...`,
`MATHEMATICAL ...` or `CIRCLED ...`. It also ran over the whole host rather
than per label, so any legitimate IDN looked "mixed" purely because its TLD is
Latin.

Replaced with real Unicode Script resolution from a generated table (958
ranges, 163 scripts, UCD 15.0.0) and **UTS-39 §5.1 Highly Restrictive applied
per label**, including the Latin+Han+Hiragana+Katakana / +Bopomofo / +Hangul
combinations. Whole-script confusables (`раураӏ.com`, which mixes nothing —
the entire label is a disguise) are a separate check, since the mixed-script
test by definition cannot see them.

Net effect: `xn--pypal-4ve.com`, `xn--pple-43d.com` and `xn--80ak6aa92e.com`
are now caught under both `strict` and `balanced`, while `例え.com`,
`한국.com`, `münchen.de` and `онлайн.com` all parse cleanly.

New codes: `MIXED_SCRIPT_LABEL`, `CONFUSABLE_HOST`, `IDNA_DISALLOWED`,
`BIDI_CONTROL_IN_HOST`, `ZERO_WIDTH_IN_HOST`, `INVALID_PUNYCODE`.

Scope stated honestly: the confusable map is a curated
Cyrillic/Greek/Armenian set, not full UTS-39 §4, which needs the UCD
`confusables.txt` data file. `skeleton()` implements the standard algorithm, so
only the table needs swapping.

## Checks removed or made opt-in

Each move came with an explicit security justification and a regression test
proving no bypass was opened.

**`enforce_query_injection` — removed.** A substring blocklist over the raw
query cannot be a defense: whether `?q=DROP TABLE` is an attack depends
entirely on the consuming application, which a URL parser cannot see. It was
trivially bypassed by re-encoding, so it provided no floor — while producing
verified false positives on ordinary input (`?q=WAITFOR`, `?filter=a--b`). It
was also the root cause of a flaky property test: the library's own tests could
not survive its default policy, which was the tell.

**`block_dangerous_ports` — now opt-in.** SSRF-to-internal-service is already
covered by `enforce_ssrf`; blocking port 22 on a *public* host prevents nothing
an attacker wants. It is deployment policy, not a URL property.

**`reject_credentials` — now opt-in.** `user:pass@host` is legal RFC 3986 and
common in internal tooling. The phishing shape that actually matters
(`https://apple.com@evil.com/`) is caught structurally by
`enforce_parser_confusion`, and `.host` correctly reports `evil.com`. A
non-blocking advisory finding is still emitted.

**`require_canonical` and `has_suspicious_punycode` — removed.** Superseded by
normalization and by the new Unicode engine respectively. The Punycode
heuristic's own test suite documented plain ASCII domains like `carnival.com`
(contains "rn") and any domain with more than two hyphens as intended flags.

## Ergonomics

- **`parse_url_local()`** replaces `parse_url_unsafe()` (retained as an alias).
  "Unsafe" was the wrong signal for parsing your own development URL — and
  under the new `local` policy it is not even unsafe.
- **New `local` policy.** Permits loopback and RFC1918 so
  `http://localhost:3000` parses, while *narrowing rather than disabling* SSRF:
  cloud metadata endpoints, the link-local range, `.internal` and kubernetes
  service names stay blocked.
- **`SecurityFinding.remediation`.** Findings now carry a machine-readable next
  step, appended to the raised message, so an SSRF rejection names the way out
  instead of leaving the caller stuck.
- All 19 exception classes are exported from the package root (was 8).

## Internals

- `_apply_overrides` re-listed all twenty policy fields by hand; a field added
  later and forgotten there would silently revert to its default, which in a
  security policy means silently disabling a check. Now `dataclasses.replace()`,
  pinned by a test driven off `dataclasses.fields(SecurityPolicy)`.
- Every `lru_cache` in the package is now reachable from `get_cache_info()` and
  `clear_all_caches()`. The new discovery-based test immediately found three
  unreported caches beyond the known `_resolve_named_policy` omission.
- `URL` gained `__copy__`, `__deepcopy__`, `__getstate__` and `__setstate__`,
  since the default implementations reconstruct slot-by-slot through
  `__setattr__` and would trip the immutability guard.

## Testing

1244 → 1599 tests. Coverage gate raised 90% → 92% (actual 94.5%). New suites:
entry-point enforcement parity across every entry point including `URL()`,
`copy()` and the `with_*` methods; policy field preservation; URL immutability
driven off `__slots__`; Unicode homograph and IDNA differential regression;
cache registry completeness; public API surface snapshot.
