# urlps 0.8.0

Release date: 2026-08-18

## Highlights

**The default security policy for `parse_url()` is now `"strict"`, not
`"balanced"`.** This is the headline, breaking change in this release — see
Migration Notes below. Alongside it: `has_suspicious_punycode()` is now
actually wired into validation (it existed since an earlier release but was
never called), and `is_open_redirect_risk()` now also checks the
percent-decoded path.

## Changed

- **Default security policy is now `strict`.** `parse_url(url)` with no
  `policy=` argument now enforces everything `strict` enforces: query
  injection heuristics, dangerous-port blocking, rejection of credentials in
  userinfo, canonical-form enforcement, and the new Punycode heuristic below
  — none of which were on by default before. Pass `policy="balanced"`
  explicitly to get the previous default behavior.
- `has_suspicious_punycode()` (confusable-character/homograph detection for
  Punycode-encoded hosts, e.g. `xn--pple-43d.com` decoding to a Cyrillic
  lookalike of `apple.com`) is now wired into `collect_security_findings()`
  via a new `SecurityPolicy.enforce_suspicious_punycode` field. It follows
  the same strict-only pattern as query injection/dangerous ports/credential
  rejection rather than being always-on like the existing mixed-script
  check, because its own test suite documents it as deliberately aggressive
  — it flags plain ASCII lookalike patterns too (e.g. `carnival.com` for
  containing "rn"), which would be too many false positives for a
  default-on, non-opt-in check.
- `is_open_redirect_risk()` now also checks the percent-decoded path, so
  `%5cevil.com` is caught the same way a raw `\evil.com` already was.

## Migration Notes

**This is a breaking change if you call `parse_url()` without an explicit
`policy=` argument and rely on any of the following having been allowed:**

| Previously allowed by default | Now requires `policy="balanced"` |
|---|---|
| `http://user:pass@example.com/` (credentials in userinfo) | ✓ |
| `HTTP://EXAMPLE.COM/`, `http://example.com:80/` (non-canonical form) | ✓ |
| `?q=<script>...`, `?redirect=javascript:...` (query injection patterns) | ✓ |
| `http://example.com:22/`, `:3306/`, `:6379/` etc. (dangerous ports) | ✓ |
| `xn--pple-43d.com` and similar Punycode homographs | ✓ |

If your code parses URLs you intend to inspect, canonicalize, or reconstruct
yourself rather than reject outright — as opposed to URLs from a source you
don't trust — pass `policy="balanced"` explicitly:

```python
url = parse_url("http://user:pass@example.com:8080/path", policy="balanced")
```

`parse_url_unsafe()` (for internal/development URLs) is unaffected — it
already defaulted to the separate, more permissive `internal` policy.

## Security Notes

- Two real gaps closed: Punycode homograph domains were previously
  undetected under every policy including `strict` (the detection function
  existed but nothing called it); percent-encoded backslashes in a path
  (`%5cevil.com`) previously bypassed the open-redirect check that already
  caught the raw form.
