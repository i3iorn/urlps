# urlps 1.1.0

Release date: 2026-08-30

## Highlights

A product review of the 1.0 line turned up a handful of real gaps: a
reintroduced SSRF bypass, a builder that could hand back unparseable
output, a comparison regression from the 1.0.1 refactor, and several
pieces of long-promised deprecation machinery that had never actually been
wired up. This release closes all of them, adds one new configuration
knob, and starts the clock on the deprecations already documented in
`MIGRATION.md`.

## Fixed

- **SSRF: trailing-dot bypass on IP literals.** `is_ssrf_risk()`
  normalized the host for its hostname-blocklist branch (stripping a
  trailing root dot) but every IP-literal branch — decimal, octal/hex, and
  the general `inet_aton`-style parser — still worked on the raw string.
  `is_ssrf_risk("10.0.0.5.")` and `is_ssrf_risk("192.168.1.1.")` returned
  `False`: the exact bypass class 1.0.0 fixed for hostnames (`evil.com.`),
  reintroduced here for numeric forms. `parse_url()` itself was never
  exploitable through this — the parser rejects a trailing dot on an IPv4
  literal as malformed before the security pass runs — but `is_ssrf_risk()`
  is exported from `_security/__init__.py` and reachable directly.
- **`build()`/`compose_url()` now validate host format.** They previously
  only normalized the host (case-fold, trailing-dot strip), never
  validated it, so `build("https", "not a valid host! <script>")` produced
  a string that `parse_url()` then refused to parse. Host format is now
  checked the same way `_parser.py` checks it during parsing (hostname
  grammar, or IPv4/IPv6 literal), raising `HostValidationError` for a
  malformed host. This is structural validation only — `build_secure()`
  remains the function that applies a security policy to an untrusted
  host.
- **Regression: `URL` no longer compared equal to a plain string.** A
  pre-1.0.1 commit added explicit string support to `__eq__`/`__lt__`/
  `__le__`/`__gt__`/`__ge__`; when those operators moved into
  `_comparison.py`'s `_URLComparison` during the 1.0.1 module
  decomposition, the `isinstance(other, str)` branch didn't come with
  them — every comparison there checked only
  `isinstance(other, type(url))`, so `url == "https://example.com/"`
  silently started returning `False`. No test caught it because none
  exercised string comparison. Restored: a `URL` now compares (and orders)
  against a plain string using `as_string()` directly, with no
  canonicalization.
- A test, `test_bracketed_host_without_port_or_closing_bracket`, asserted
  `get_canonical_url("http://[::1]extra/path")` returns a non-`None`
  result. Its premise didn't hold: stdlib's `urlparse()` raises
  `ValueError: Invalid IPv6 URL` for that input before
  `get_canonical_url` reaches the branch the test meant to exercise, so
  the function correctly failed closed and returned `None` — not a bug.
  Corrected the assertion.
- CI's `pull_request`/`push` triggers were scoped to `master` only, but the
  repository's own branch policy requires every PR into `master` to come
  from `dev` — so every feature-branch PR into `dev`, the actual
  integration branch, got zero CI signal. `dev` is now included in both
  trigger filters.

## Added

- `URLPS_PHISHING_DATABASE_URL` environment variable overrides the feed
  `check_phishing=True` downloads hostnames from. Previously this was a
  single hardcoded third-party URL (`phish.co.za`) with no override
  anywhere — every other length-limit/cache-size constant in the package
  is `URLPS_*`-overridable, this one wasn't. Must be `http://` or
  `https://`; invalid values fall back to the default with a
  `RuntimeWarning`. Read once at import time, like the other `URLPS_*`
  variables. Documented in the README and in SECURITY.md's note on
  `check_phishing`'s trust model.
- CI now installs the package **without** the `idna` extra and runs
  `tests/security/test_idna_fallback.py` against it. The stdlib-only IDNA
  2003 fallback in `_security/_unicode/uts46.py` had zero test coverage —
  both its branches were `# pragma: no cover - depends on the install`,
  since the `dev` extra hard-requires `idna`. That fallback is exactly the
  class of security-relevant differential 1.0.0 fixed
  (`straße.de` → `strasse.de` under stdlib IDNA 2003 vs. the
  `xn--strae-oqa.de` browsers use under UTS-46), so it deserved real
  coverage. The pragmas are gone; both code paths now run in every CI
  build.
- README section, "Using `check_dns`/`check_phishing` from `asyncio`
  code": both options do blocking network I/O (DNS resolution plus a
  verification connect; a synchronous HTTP download), with no prior
  guidance for `asyncio`-based callers — exactly the audience most likely
  to call `parse_url()` from inside an async request handler and
  unknowingly stall the event loop. Shows the `run_in_executor` pattern.
- `url == "https://..."` and friends are now documented in the README's
  URL Methods table.

## Deprecated

Three pieces of backward-compatibility surface that have been documented
as superseded since 1.0.0 (see `MIGRATION.md`) now actually say so at
runtime, via `DeprecationWarning`, instead of only in prose:

- **`parse_url_unsafe()`** — deprecated alias for `parse_url_local()`.
  Behavior is unchanged (it delegates to `parse_url_local()` exactly); only
  the name is discouraged. Planned for removal in 2.0.
- **`SecurityPolicy(enforce_suspicious_punycode=True)`** — this field has
  gated nothing since 1.0.0 (superseded by `enforce_mixed_scripts` and
  `enforce_confusable_host`'s real UTS-39 script/confusable analysis).
  Passing `True` now warns instead of silently no-opping; the default
  (`False`) does not warn. Planned for removal in 2.0.
- **`has_suspicious_punycode()`** — predates and is weaker than the
  homograph detection `parse_url()` actually enforces (hardcoded
  suspicious-TLD and brand-name lists vs. real script analysis). Use
  `urlps._security.host_analysis.analyze_host()` instead. Planned for
  removal in 2.0.

None of these change behavior for existing callers — every deprecated path
still works exactly as before. See `MIGRATION.md` for the full
renamed-and-deprecated table.

## Security Notes

The SSRF trailing-dot fix hardens `is_ssrf_risk()` against a private-IP
bypass on numeric host forms reachable only by direct callers of that
function; `parse_url()`'s own SSRF enforcement was not affected, since the
parser already rejects the malformed input earlier. No previously-accepted
`parse_url()` input is rejected differently by this release.

## Migration Notes

- If you call `build()`/`compose_url()` with a host that isn't a
  syntactically valid hostname or IP literal, you will now get a
  `HostValidationError` instead of a string that silently failed to
  round-trip through `parse_url()`. If you were relying on the old
  behavior, validate or sanitize the host before calling `build()`, or
  catch `HostValidationError`.
- If you call `has_suspicious_punycode()`, `parse_url_unsafe()`, or
  construct `SecurityPolicy(enforce_suspicious_punycode=True)` directly,
  you'll now see a `DeprecationWarning`. Nothing else changes; migrate at
  your own pace before 2.0.
